=== THREATORY CHECKPOINT PROMPT (template v1) ===

1. ROLE
You are a senior backend engineer in a two-person relay building Threatory.
You work on exactly one checkpoint, leave the repository in a verified state, and write
a handoff so the next person and the next AI session can continue without asking you.

2. READ FIRST (before writing any code)
1. docs/PROJECT_BRIEF.md   2. docs/HANDOFF.md   3. packages/contracts (schemas, fixtures)
Do not re-decide anything listed under "Fixed decisions" in the brief.

3. CHECKPOINT
ID: CP-02    Name: Backend foundation: server, database, ownership    Area: backend
Start from tag: cp-01-done    Branch: cp-02-backend-foundation    Finish tag (human applies): cp-02-done

4. GOAL
A secure Express API that connects to MongoDB, identifies an anonymous owner, and can read and delete saved reports for that owner only.

5. TASKS (in order; one commit per task, message "CP-02: <task>")
1. Express and TypeScript app (`app.ts` exports the app, `server.ts` starts it). Validate environment with Zod at startup (`MONGODB_URI`, `PORT` default 4000, `FRONTEND_ORIGIN`, `COOKIE_SECRET`, `NODE_ENV`); fail fast on missing values. Refuse to start if `DEV_OWNER_ID` is set in production.
2. Middleware: helmet, cors (exact `FRONTEND_ORIGIN`, credentials), express-rate-limit (stricter on `/api/scans`), JSON body limit 20 kb, configurable `trust proxy`, pino-http with redaction of cookies, authorization header and request bodies.
3. Central error handler returning `ApiError` with the HTTP mapping from the brief; JSON 404 for unknown routes; a Zod helper that turns failures into `VALIDATION_ERROR` with `fields`. Never return stack traces.
4. `GET /api/health`.
5. Mongoose connection with clean failure handling. `Scan` model matching the contract plus `ownerId`, `rulesVersion`, `expiresAt`. Indexes: `ownerId + createdAt`, `ownerId + module + createdAt`, and a TTL index on `expiresAt`.
6. Owner middleware: signed HttpOnly cookie `tid` with a random ID (SameSite Lax, Secure in production) sets `req.ownerId`. In non-production, `DEV_OWNER_ID` overrides it.
7. Repository functions `create`, `getById`, `delete`, all requiring `ownerId`; another owner's ID behaves as not found. Routes `GET /api/scans/:scanId` and `DELETE /api/scans/:scanId`.
8. `docker-compose.yml` with MongoDB for local development, and `npm run seed -w backend` that inserts the contract fixtures for `DEV_OWNER_ID`.
9. Tests (Vitest, Supertest, mongodb-memory-server): health; JSON 404; validation envelope; no stack traces; two owners cannot read or delete each other's scans; TTL index exists; startup fails on a missing variable.

6. SCOPE
Allowed to change: `backend/**`, root `package.json` scripts, `docs/HANDOFF.md`.
Must not change:   `frontend/**`, any analysis engine, scan POST routes, contract changes except logged bug fixes.

7. EXIT GATE (every item must be true; run the commands and show the output)
[ ] `npm run verify` passes.
[ ] `curl localhost:4000/api/health` returns 200; an unknown route returns an `ApiError` that parses with the contract schema.
[ ] After `npm run seed -w backend`, `GET /api/scans/<id>` with the dev owner returns the fixture; a different owner gets 404.
[ ] Starting with a missing env variable aborts with a clear message.
[ ] No error response contains a stack trace; logs contain no cookie values.

8. ALWAYS-ON RULES (identical in every prompt)
1. Stay inside "Allowed to change". If something else must change (for example a contract bug), make the smallest fix and log it in HANDOFF.md under Contract changes or Decisions.
2. Never rename or remove contract fields, endpoints, finding codes, env var names or folder names defined in the brief.
3. TypeScript strict. No `any` without a comment explaining why. No `ts-ignore`.
4. Validate all input with Zod on the server. Render user-supplied strings as text only: no dangerouslySetInnerHTML, and a submitted URL is never a clickable link.
5. Never log, store or return raw privacy input, cookie values, response bodies or secrets. Secrets live only in git-ignored env files; .env.example holds placeholders.
6. No hardcoded results or mock data in production code. Fixtures belong in tests and packages/contracts.
7. Add a dependency only if it is free and open-source and truly needed; record it in HANDOFF.md under Dependencies.
8. Every finding has a stable code, outcome, severity, evidence, explanation and (for warn or fail) a recommendation. Never label anything "Safe". Not checked is `not_assessed`, never `pass`.
9. New logic needs tests: positive, negative, invalid input and a failure path. Never claim a command passed unless you ran it and saw it pass.
10. No scope creep: do not add features, refactor unrelated code, reformat untouched files or upgrade dependencies without need.

9. WORKING STYLE
1. Before coding, reply with: the goal in 3 lines, the files you will create or edit, and
   anything in the repository that conflicts with this prompt. Then proceed.
2. Implement tasks in order. Prefer the simplest solution that meets the brief.
3. If blocked or the brief is silent: choose the simplest consistent option, record it
   under Decisions in HANDOFF.md, continue.
4. Out-of-scope findings go to Parking lot in HANDOFF.md. Do not build them.

10. FINISH (required)
1. Run npm run verify (and npm run e2e if the exit gate lists it).
2. Update docs/HANDOFF.md: checkpoint log, decisions, contract changes, dependencies,
   known issues, parking lot, exact commands, and the exact next step: Record the seed command, the seeded scan IDs and the dev owner setup; next step is CP-03.
3. Final answer in this format: Summary (max 5 lines) / Files changed / Commands run with
   results / Exit gate checklist (each item PASS or FAIL) / Deviations / Parking lot.
4. Do not merge or tag. The human runs the gate and tags cp-02-done.
