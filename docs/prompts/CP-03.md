=== THREATORY CHECKPOINT PROMPT (template v1) ===

1. ROLE
You are a senior frontend engineer in a two-person relay building Threatory.
You work on exactly one checkpoint, leave the repository in a verified state, and write
a handoff so the next person and the next AI session can continue without asking you.

2. READ FIRST (before writing any code)
1. docs/PROJECT_BRIEF.md   2. docs/HANDOFF.md   3. packages/contracts (schemas, fixtures)
Do not re-decide anything listed under "Fixed decisions" in the brief.

3. CHECKPOINT
ID: CP-03    Name: Frontend foundation: shell, design system, report view    Area: frontend
Start from tag: cp-02-done    Branch: cp-03-frontend-foundation    Finish tag (human applies): cp-03-done

4. GOAL
A responsive app shell, a typed API client and the shared report components, proven by a fully working report page that renders any saved report from the backend.

5. TASKS (in order; one commit per task, message "CP-03: <task>")
1. Next.js App Router with TypeScript (strict), Tailwind, shadcn/ui, lucide-react and a TanStack Query provider. Placeholder routes: `/`, `/url-analyzer`, `/privacy-analyzer`, `/website-auditor`, `/history`, `/reports/[scanId]`, `/help`.
2. App shell: responsive navigation with Threatory branding, active state and page header. Professional light theme with restrained status colours.
3. `next.config` rewrites `/api/:path*` to `API_ORIGIN` (default `http://localhost:4000`); add `frontend/.env.example`.
4. API client in `src/lib/api-client.ts`: relative fetch with credentials, timeout, responses parsed with the contract schemas, `ApiError` codes mapped to friendly messages, a typed error, and an "unexpected response" error for malformed data.
5. Shared components in `src/components/reports`: `OutcomeBadge`, `SeverityBadge` (icon plus text, never colour alone), `FindingCard`, `FindingGroup` (by category), `AssessmentHeader` (label, riskLevel, optional score with meaning), `LimitationsPanel`, `PartialBanner`, `EmptyState`, `ErrorState`, skeleton loaders.
6. Make `/reports/[scanId]` fully work via `GET /api/scans/:scanId` with loading, not-found, error and retry states, and `details` shown as a simple key-value list.
7. A small "API status" indicator in the shell using `/api/health`.
8. Tests (Vitest, React Testing Library, vitest-axe): every contract fixture renders; `not_assessed` is visibly different from `pass`; client error mapping; shell navigation.

6. SCOPE
Allowed to change: `frontend/**`, `docs/HANDOFF.md`.
Must not change:   `backend/**`, `packages/contracts` (except logged bug fixes), the module input forms.

7. EXIT GATE (every item must be true; run the commands and show the output)
[ ] `npm run verify` passes.
[ ] With the backend running and seeded, `/reports/<id>` renders the completed, partial and failed fixtures correctly; an unknown ID shows a not-found state.
[ ] `not_assessed` findings are clearly distinct from `pass`; the whole app works by keyboard alone.
[ ] The API status indicator turns to an error state when the backend is stopped.
[ ] No axe violations in component tests.

8. ALWAYS-ON RULES (identical in every prompt)
1. Stay inside "Allowed to change". If something else must change (for example a contract bug), make the smallest fix and log it in HANDOFF.md under Contract changes or Decisions.
2. Never rename or remove contract fields, endpoints, finding codes, env var names or folder names defined in the brief.
3. TypeScript strict. No `any` without a comment explaining why. No `ts-ignore`.
4. Validate all input with Zod on the server. Render user-supplied strings as text only: no dangerouslySetInnerHTML, and a submitted URL is never a clickable link.
5. Never log, store or return raw privacy input, cookie values, response bodies or secrets. Secrets live only in git-ignored env files; .env.example holds placeholders.
6. No hardcoded results or mock data in production code. Fixtures belong in tests and packages/contracts.
7. Add a dependency only if it is free and open-source and truly needed; record it in HANDOFF.md under Dependencies.
8. Every finding has a stable code, outcome, severity, evidence, explanation and (for warn or fail) a recommendation. Never label anything "Safe". Not checked is `not_assessed`, never `pass`.
9. New logic needs tests: positive, negative, invalid input and a failure path. Never claim a command passed unless you ran it and saw it pass.
10. No scope creep: do not add features, refactor unrelated code, reformat untouched files or upgrade dependencies without need.

9. WORKING STYLE
1. Before coding, reply with: the goal in 3 lines, the files you will create or edit, and
   anything in the repository that conflicts with this prompt. Then proceed.
2. Implement tasks in order. Prefer the simplest solution that meets the brief.
3. If blocked or the brief is silent: choose the simplest consistent option, record it
   under Decisions in HANDOFF.md, continue.
4. Out-of-scope findings go to Parking lot in HANDOFF.md. Do not build them.

10. FINISH (required)
1. Run npm run verify (and npm run e2e if the exit gate lists it).
2. Update docs/HANDOFF.md: checkpoint log, decisions, contract changes, dependencies,
   known issues, parking lot, exact commands, and the exact next step: Record the component list and how to view seeded reports; next step is CP-04.
3. Final answer in this format: Summary (max 5 lines) / Files changed / Commands run with
   results / Exit gate checklist (each item PASS or FAIL) / Deviations / Parking lot.
4. Do not merge or tag. The human runs the gate and tags cp-03-done.
